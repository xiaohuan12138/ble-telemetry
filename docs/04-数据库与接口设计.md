# 第 4 章 数据库与接口设计

## 4.1 数据库选型

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| SharedPreferences | 极简 | 只能存键值对，无法查询、无类型安全 | 仅用于偏好设置 → 改用 DataStore |
| SQLiteOpenHelper | 原生、可控 | 手写 SQL 与对象映射，样板代码巨多，编译期无校验 | ❌ |
| **Room** | 编译期校验 SQL、返回 Flow、协程原生、LiveData/Flow 自动刷新 | 需 KSP 注解处理器 | ✅ 采用 |
| Realm / ObjectBox | 快 | 引入第三方引擎、体积大、学习目标偏离 | ❌ |

**Room 的决定性优势**：DAO 方法可以直接返回 `Flow<List<T>>`，数据库内容变化时自动重新发射，UI 完全不用手动刷新。底层由 SQLite trigger + Room 的 `InvalidationTracker` 实现。这一条直接消灭了"插入后要记得 notifyDataSetChanged"这类经典 bug。

**DataStore 取代 SharedPreferences**：SharedPreferences 的 `commit()` 是同步 IO，`apply()` 虽异步但可能丢数据且无事务保证。DataStore 基于协程 + Flow，全异步、类型安全（Proto/Preferences）、有事务。

## 4.2 E-R 关系

```
┌─────────────────────┐          ┌─────────────────────┐
│      devices        │          │       rules         │
│─────────────────────│          │─────────────────────│
│ PK address  TEXT    │          │ PK id       INTEGER │
│    name     TEXT    │          │    name     TEXT    │
│    lastSeenAt INTEGER│         │    channel  TEXT    │
│    lastRssi INTEGER │          │    operator TEXT    │
│    connectCount INT │          │    threshold REAL   │
│    isFavorite BOOL  │          │    enabled  BOOL    │
└──────────┬──────────┘          │    ...              │
           │                      └─────────────────────┘
           │ 1 : N（逻辑关联，非外键约束）
           ▼
┌─────────────────────┐
│      readings       │
│─────────────────────│
│ PK id      INTEGER  │
│    deviceAddress TEXT│  ← 建索引
│    timestamp INTEGER│  ← 建索引
│    temperature REAL │
│    humidity   REAL  │
│    pressure   REAL  │
│    lux        INT   │
│    tempBmp    REAL  │
│    flags      INT   │
│    rssi       INT   │
│    source     TEXT  │
└─────────────────────┘
```

**为什么 `readings.deviceAddress` 不用真正的外键约束**：如果加了 `ForeignKey(onDelete = CASCADE)`，删除一个设备会连带删掉它的全部历史读数——这不是我们想要的行为。历史数据是有价值的，设备记录只是缓存。所以用逻辑关联 + 索引。

**索引设计**：
- `deviceAddress` 索引 → 加速"只看某台设备的历史"
- `timestamp` 索引 → 加速 `ORDER BY timestamp DESC` 和范围统计

## 4.3 表结构详解

### 4.3.1 `readings`（采样记录表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER PK 自增 | — |
| `deviceAddress` | TEXT | 来源设备 MAC |
| `timestamp` | INTEGER | 本地接收时刻（毫秒） |
| `temperature` | REAL | 温度 ℃（优先 AHT20） |
| `humidity` | REAL | 相对湿度 % |
| `pressure` | REAL | 气压 hPa |
| `lux` | INTEGER | 光照 lux |
| `tempBmp` | REAL | BMP280 温度（第二温度源） |
| `flags` | INTEGER | 传感器健康位（bit0=AHT20, bit1=BMP280, bit2=BH1750） |
| `rssi` | INTEGER | 接收时信号强度 dBm |
| `source` | TEXT | `ble` / `mock`，区分真实数据与演示数据 |

**为什么不只存最终温度**：保留 `tempBmp` 是为了事后能回看"两个温度传感器是否一致"。若只存一个合并后的值，就无法诊断"某颗芯片漂移"这类硬件故障。这是诊断信息的价值。

### 4.3.2 `rules`（自动化规则表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER PK 自增 | — |
| `name` | TEXT | 规则名，如"机房高温报警" |
| `channel` | TEXT | 监测通道枚举名：`TEMPERATURE`/`HUMIDITY`/`PRESSURE`/`LUX` |
| `operator` | TEXT | 比较符枚举名：`GT`/`LT` |
| `threshold` | REAL | 阈值 |
| `enabled` | BOOL | 总开关 |
| `notifyEnabled` | BOOL | 触发时发通知 |
| `ledEnabled` / `ledBrightness` | BOOL / INT | 触发时控灯 |
| `buzzerEnabled` / `buzzerDurationMs` | BOOL / INT | 触发时鸣响 |
| `triggerCount` | INT | 累计触发次数（统计用） |

**枚举存 name 字符串而非序数**：存 `ordinal`（0/1/2）虽然省空间，但一旦将来调整枚举顺序，老数据全部错位。存 name 字符串可读、可迁移，代价只是几个字节。

### 4.3.3 `devices`（已知设备表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `address` | TEXT PK | MAC 地址天然唯一，直接当主键 |
| `name` | TEXT | 广播名 |
| `lastSeenAt` | INTEGER | 最后一次见到它的时间 |
| `lastRssi` | INTEGER | 最后一次的信号强度 |
| `connectCount` | INTEGER | 累计连接次数 |
| `isFavorite` | BOOL | 收藏标记 |

## 4.4 DAO 接口设计

### 4.4.1 `ReadingDao`

| 方法 | 返回 | 说明 |
|------|------|------|
| `insert(reading)` | `suspend Long` | 插入单条，冲突替换 |
| `observeRecent(limit)` | `Flow<List>` | 最近 N 条，**新增自动刷新 UI** |
| `observeByDevice(address, limit)` | `Flow<List>` | 按设备筛选 |
| `count()` | `suspend Int` | 总数 |
| `statsSince(since)` | `suspend RangeStats?` | 区间极值，**SQL 聚合** |
| `keepLatest(keep)` | `suspend` | 数据裁剪 |
| `clearAll()` | `suspend` | 清空 |

**`statsSince` 为什么用 SQL 聚合**：

```sql
SELECT MIN(temperature) as minT, MAX(temperature) as maxT,
       MIN(humidity) as minH, MAX(humidity) as maxH
FROM readings WHERE timestamp >= :since
```

若把几千条读进 Kotlin 再遍历，要分配几千个对象、跑两次 O(n) 循环；交给 SQLite 在 C 层算，既快又省内存。这是移动端数据处理的正确姿势。

**`keepLatest` 为什么必要**：1Hz 采样跑一天就是 86400 条。不裁剪，数据库会无限膨胀，最终拖慢查询、占满用户存储。由 `DatabaseCleanupWorker` 定期调用。

### 4.4.2 `RuleDao` / `DeviceDao`

- `RuleDao.upsert` —— Room 2.5+ 提供 `@Upsert`（存在即更新，否则插入），省去手写冲突处理
- `RuleDao.getEnabled()` —— 用 `suspend` 而非 `Flow`：规则引擎每次评估都读一次，不需要持续观察
- `DeviceDao.incrementConnectCount` —— 用 SQL 自增而非"读出来+1再写回"，避免并发下丢更新

## 4.5 数据库版本与迁移

```kotlin
@Database(entities = [ReadingEntity::class, RuleEntity::class, DeviceEntity::class], version = 1)
abstract class AppDatabase : RoomDatabase() {
    abstract fun readingDao(): ReadingDao
    abstract fun ruleDao(): RuleDao
    abstract fun deviceDao(): DeviceDao
}
```

当前 `version = 1`，尚未产生需要迁移的线上数据，故未编写 Migration。若后续加字段，正确做法是：

```kotlin
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE readings ADD COLUMN altitude REAL NOT NULL DEFAULT 0")
    }
}
Room.databaseBuilder(...).addMigrations(MIGRATION_1_2).build()
```

开发期可用 `fallbackToDestructiveMigration()` 图方便，但**正式版本禁止**——它会直接删库，用户数据全丢。

## 4.6 BLE 接口设计（GATT 约定）

两端必须严格一致。Android 侧定义在 `ble/GattSpec.kt`，ESP32 侧定义在 `firmware/include/config.h`。

### 4.6.1 服务与特征

| UUID | 类型 | 属性 | 方向 | 说明 |
|------|------|------|------|------|
| `0000FF10-...` | Service | — | — | 传感器服务 |
| `0000FF11-...` | Char | **Notify** | ESP32 → 手机 | 传感器数据帧（分包推送） |
| `0000FF12-...` | Char | Read / Write | 双向 | 采样周期（毫秒，4 字节） |
| `0000FF20-...` | Service | — | — | 控制服务 |
| `0000FF21-...` | Char | **Write** | 手机 → ESP32 | 命令帧（LED/蜂鸣/周期/强制上报） |
| `0000180A-...` | Service | — | — | 标准 Device Information |
| `0000180F-...` | Service | — | — | 标准 Battery |
| `00002902-...` | Descriptor | Write | 手机 → ESP32 | **CCCD**，订阅开关 |

**为什么传感器与控制分成两个 Service**：语义清晰；将来加 OTA 服务时不会污染现有结构；nRF Connect 里查看时分组一目了然。

**为什么用 128 位自定义 UUID**：16 位 UUID 由蓝牙 SIG 统一分配，留给标准服务；私有服务必须用 128 位，否则会与未来的标准服务撞车。

### 4.6.2 CCCD 两步走（易错点）

订阅 Notify 必须做**两件事**，缺一不可：

```kotlin
// ① 告诉手机本地协议栈：我要接收这个特征的通知
bluetoothGatt.setCharacteristicNotification(char, true)

// ② 告诉对端设备：请开始推送
val desc = char.getDescriptor(GattSpec.DESCRIPTOR_CCCD)
desc.value = BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE
bluetoothGatt.writeDescriptor(desc)
```

**典型症状**：只做 ① → 连接成功、服务发现成功，但永远收不到数据。这个问题在调试中极常见。

### 4.6.3 命令帧清单

| 命令 | 值 | Payload | 说明 |
|------|----|---------|------|
| `CMD_SET_LED` | `0x10` | `[enable(1), brightness(1)]` | LED 开关 + 亮度 0-255 |
| `CMD_SET_BUZZER` | `0x11` | `[durationMs_be16]` | 蜂鸣器鸣响时长 |
| `CMD_SET_PERIOD` | `0x12` | `[periodMs_be32]` | 采样周期 |
| `CMD_FORCE_REPORT` | `0x13` | 空 | 立即上报一帧 |

ESP32 执行后回 `TYPE_ACK`（`0x41`），payload 为状态码：`0x00` 成功，`0x01` CRC 错，`0x02` 未知类型，`0x03` 长度错，`0x04` 参数错。
