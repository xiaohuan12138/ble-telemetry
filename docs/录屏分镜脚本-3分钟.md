## 镜 1｜项目介绍（18 秒）

**画面**：切到 PPT 第 2、3 页（项目概述 / 系统架构）

**操作**：缓慢翻页

**旁白**：
> 系统分两端。下位机是 ESP32，通过 I2C 接三颗传感器——AHT20 测温湿度、BMP280 测气压、BH1750 测光照，同时驱动 LED 和蜂鸣器。上位机是 Android App，用原生 Kotlin 开发，采用 MVVM 加 Repository 架构。中间通过自定义二进制协议通信，每一帧 20 字节，带 CRC16 校验。

**要点**：说清"两端 + 协议"，不要念 PPT。

## 镜 2｜扫描设备（20 秒）

**画面**：模拟器手机画面

**操作**：
1. 打开 SensorHub App（0:32）
2. 如果首次打开，会弹权限请求 → **点"允许"**（0:35）
3. 底部导航切到「设备」（0:40）
4. 点击扫描按钮（0:42）
5. 等待列表出现（0:45）

**旁白**：
> 打开 App 后先申请蓝牙和通知权限。进入设备页点击扫描，这里能看到周边广播的 BLE 设备，列表显示设备名、MAC 地址、信号强度 RSSI，并用三格信号图标表示强弱。

**要点**：
- 扫描前先确认已开启「模拟数据源」（设置页开关），否则模拟器扫不到设备
- 列表要出现至少 2 台设备才好看

## 镜 3｜连接与实时数据（30 秒）

**画面**：手机画面 · 设备详情页

**操作**：
1. 点击 `SensorHub-01`（0:52）
2. 进入详情页（0:54）
3. 点击「连接」按钮（0:56）
4. **等待 8-10 秒，让曲线滚起来**（0:58–1:08）
5. 鼠标轻扫数值卡片区域（1:10）
6. 停留看曲线滚动（1:12–1:18）

**旁白**：
> 点进详情页建立 GATT 连接：先发现服务，再订阅 Notify 特征。这里有个关键点——订阅必须做两步，先调用 setCharacteristicNotification 告诉本地协议栈，再往 CCCD 描述符写入使能值告诉对端设备开始推送。只做第一步的话，会连上但永远收不到数据。
>
> 现在看到温度 25.9 度，曲线在实时滚动，下方显示链路质量：丢包 0.0%，CRC 错误 0.0%。

**要点**：这是全片最重要的镜头，**必须等曲线真的滚起来**再解说，否则没有说服力。

## 镜 4｜反向控制（25 秒）

**画面**：手机画面 · 详情页下半部分

**操作**：
1. 拖动 LED 亮度滑块到 80%（1:22）
2. 点击「蜂鸣器」按钮（1:28）
3. 切换滤波模式单选：原始值 → 卡尔曼（1:33）
4. 指着曲线变化说（1:36）

**旁白**：
> 往下是反向控制。拖动滑块可以改变 LED 亮度，手机会组一个命令帧写进控制特征，ESP32 解析后调整 PWM 占空比。点蜂鸣器会下发时长参数，蜂鸣器响一声后回 ACK。
>
> 这里还能实时切换滤波模式：原始值抖动明显，切到卡尔曼滤波后曲线立刻平滑，而且响应只滞后大约三个周期。

**要点**：切换滤波时曲线会有肉眼可见的变化，**这个对比是全片第二个高潮**。

## 镜 5｜规则与历史（20 秒）

**画面**：手机画面

**操作**：
1. 底部导航切「规则」（1:47）
2. 点新增，填一条"温度 > 30℃ → 蜂鸣 + 通知"（1:50）
3. 保存（1:55）
4. 切「历史」（1:58）
5. 上下滑动列表（2:00）

**旁白**：
> 规则页可以配置自动化：比如温度超过 30 度就触发蜂鸣和通知。规则引擎做了三重防抖——要连续命中 N 次才算达标，触发后有 5 秒冷却，还有滞回比较避免温度在阈值附近反复横跳。
>
> 历史页的数据来自 Room 数据库，DAO 直接返回 Flow，新增记录时列表自动刷新，不用手动 notify。

**要点**：规则新增对话框要完整展示一遍字段。

## 镜 6｜桌面小组件（20 秒）

**画面**：手机桌面

**操作**：
1. 按 Home 回到桌面（2:07）
2. 长按桌面空白处 → 小组件（2:10）
3. 找到 SensorHub，拖到桌面（2:14）
4. 等 3-5 秒看数值跳动（2:17）
5. 点击小组件回到 App（2:22）

**旁白**：
> 这是伴生模块 P1 桌面小组件。小组件运行在桌面进程，只能通过 RemoteViews 远程描述界面。因为系统自动刷新的最小间隔是 30 分钟，对实时数据没意义，所以我改成由服务在收到数据时主动推送，实现秒级刷新。
>
> 需要说明的是，小组件目前用的是进程内静态缓存，App 进程被回收后会显示暂无数据。更健壮的做法是存进 Room 由小组件自己查询，这需要引入 RemoteViewsService，复杂度会上升，属于明确的技术取舍。

**要点**：**主动说出局限**，比被老师问出来好得多。

## 镜 7｜技术亮点（25 秒）

**画面**：切回 PPT 第 4、5、6 页

**操作**：慢速翻页，每页停 8 秒

**旁白**：
> 回头说三个核心技术点。
>
> 第一是协议。我用的是二进制帧而不是 JSON——一帧 20 字节刚好一个 BLE 包，JSON 要 45 字节得拆三包。浮点数统一放大十倍转整数传，避免精度丢失和字节序歧义。
>
> 第二是流式解析。BLE 的分包边界和协议帧边界毫无关系，可能一次来半帧也可能来两帧半，所以必须有累积缓冲区。关键是 CRC 校验失败时我只丢一个字节，而不是清空缓冲区——这样可以抢救后面已经收到的好数据，这是滑动窗口思想。
>
> 第三是卡尔曼滤波。五个公式，Q 取 0.01 因为室内温度每秒变化远小于这个量级，R 取 0.1 因为 AHT20 标称精度正负 0.3 度。卡尔曼增益会自动收敛，刚开始接近 1 全信测量，后来逐渐变小越来越信预测。

**要点**：这是全片技术密度最高的部分，语速放慢，让老师听清。

## 常见翻车点

| 问题 | 预防 |
|------|------|
| 模拟器 BLE 扫不到 | 必须先在设置页开启「模拟数据源」 |
| 连接后没数据 | 检查是不是忘了开模拟数据源；真机则检查 CCCD |
| 曲线不动 | 等够 10 秒，1Hz 采样需要时间积累 |
| 小组件加不上 | 部分模拟器 Launcher 不支持长按添加，改用真机或换 Launcher |
| 录到桌面通知弹窗 | 录制前开启「勿扰模式」 |
| 忘记学号水印 | 用 OBS 加文本源，固定在右上角，录前检查一遍 |
