# 第 3 章 系统设计

## 3.1 总体架构

系统分为**下位机（ESP32）**与**上位机（Android）**两端，中间通过自定义二进制协议通信。

```
┌──────────────────────────┐          ┌──────────────────────────┐
│      ESP32 下位机         │          │      Android 上位机       │
│                          │          │                          │
│  ┌────────────────────┐  │          │  ┌────────────────────┐  │
│  │  传感器层 sensors   │  │          │  │  UI 层 (Fragment)  │  │
│  │  AHT20 / BMP280    │  │          │  └─────────┬──────────┘  │
│  │  BH1750            │  │          │  ┌─────────▼──────────┐  │
│  └─────────┬──────────┘  │          │  │ ViewModel (StateFlow)│ │
│  ┌─────────▼──────────┐  │          │  └─────────┬──────────┘  │
│  │  协议层 protocol    │  │          │  ┌─────────▼──────────┐  │
│  │  组帧 / 解析 / CRC  │  │          │  │ Repository / Domain │ │
│  └─────────┬──────────┘  │          │  └─────────┬──────────┘  │
│  ┌─────────▼──────────┐  │          │  ┌─────────▼──────────┐  │
│  │  BLE Server        │◀─┼──GATT────┼─▶│  BLE Client         │  │
│  │  (NimBLE)          │  │  Notify  │  │  Scanner/Connection │  │
│  └─────────┬──────────┘  │  Write   │  └────────────────────┘  │
│  ┌─────────▼──────────┐  │          │  ┌────────────────────┐  │
│  │  执行器 actuators   │  │          │  │  Room / DataStore   │  │
│  │  LED(PWM) / Buzzer │  │          │  └────────────────────┘  │
│  └────────────────────┘  │          │                          │
└──────────────────────────┘          └──────────────────────────┘
```

两端共用**同一套协议定义**：`firmware/include/config.h` 与 `android/.../protocol/Frame.kt` 中的常量必须严格一致，改一端必须同步改另一端。这是本项目的核心约定。

## 3.2 Android 端分层

采用 **MVVM + Repository** 模式，单向数据流。

| 层 | 职责 | 关键类 |
|----|------|--------|
| UI 层 | 渲染、收集 Flow、响应用户操作 | 5 个 Fragment、3 个 Adapter、`RealtimeChartView` |
| ViewModel 层 | 持有 UI 状态（`StateFlow<UiState>`），`viewModelScope` 起协程 | `DeviceListViewModel`、`DeviceDetailViewModel`、`RulesViewModel`、`HistoryViewModel`、`SettingsViewModel` |
| Domain 层 | 纯业务逻辑，不依赖 Android API，**可单元测试** | `Filter`（卡尔曼）、`RuleEngine`、`ReconnectPolicy` |
| Data 层 | 数据源封装 | `SensorRepository`、`SettingsRepository`（DataStore） |
| BLE 层 | 蓝牙通信细节 | `BleScanner`、`BleConnection`、`BleConnectionManager`、`MockDataSource` |
| Protocol 层 | 帧编解码 | `Crc16`、`Frame`、`FrameParser` |
| 持久化层 | Room 数据库 | `AppDatabase`、3 个 Entity、3 个 DAO |

**依赖方向**：UI → ViewModel → Repository → {BLE / Room / Domain}。下层不反向依赖上层。

## 3.3 关键类设计

### 3.3.1 `BleConnection` —— 单次连接的生命周期封装

一个 `BleConnection` 对象代表**与一台设备的一次连接尝试**。之所以不把它做成单例，是因为要支持多设备：每台设备一个实例，由 `BleConnectionManager` 统一持有。

```kotlin
class BleConnection(
    private val context: Context,
    private val device: BluetoothDevice
) {
    private val _frames = MutableSharedFlow<Frame>(extraBufferCapacity = 64)
    val frames: SharedFlow<Frame> = _frames.asSharedFlow()

    private val _state = MutableStateFlow<ConnectionState>(ConnectionState.Idle)
    val state: StateFlow<ConnectionState> = _state.asStateFlow()

    suspend fun connect(): Boolean { /* ... */ }
    suspend fun enableNotification(char: UUID): Boolean { /* CCCD 两步走 */ }
    suspend fun write(char: UUID, data: ByteArray): Boolean { /* ... */ }
    fun disconnect() { /* ... */ }
}
```

**关键设计**：GATT 回调是 Java 回调接口，且**必须在同一线程排队执行**（Android 官方要求：同一时刻只能有一个 GATT 操作在飞）。本项目用 `callbackFlow` + `Channel` 把回调转成协程可挂起的 `suspend` 函数，调用方写起来是同步顺序的：

```kotlin
suspend fun enableNotification(charUuid: UUID): Boolean {
    val char = getCharacteristic(charUuid) ?: return false
    bluetoothGatt?.setCharacteristicNotification(char, true) ?: return false   // ① 本地打开
    val desc = char.getDescriptor(GattSpec.DESCRIPTOR_CCCD) ?: return false
    desc.value = BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE
    return writeDescriptor(desc)                                                // ② 告诉对端
}
```

### 3.3.2 `BleConnectionManager` —— 多设备连接调度

```kotlin
class BleConnectionManager(private val context: Context) {
    private val connections = ConcurrentHashMap<String, BleConnection>()

    fun connectionFor(address: String): BleConnection   // 复用或新建
    suspend fun sendCommand(address: String, frame: ByteArray): Boolean
    fun drop(address: String)
}
```

用 `ConcurrentHashMap` 而非普通 Map：BLE 回调在 Binder 线程，UI 在主线程，可能被并发访问。

### 3.3.3 `FrameParser` —— 流式解析

**为什么不能"收到一包就当作一帧"**：BLE Notify 有 MTU 限制（默认 23 字节有效载荷），一帧 20 字节的数据可能被拆成两包；反过来，也可能一包里带了帧尾 + 下一帧的帧头。直接按包解析会丢数据。

**解法**：维护一个累积缓冲区，采用滑动窗口找帧头：

```
收到字节流 → 追加到 buffer
    ↓
从 buffer 头部找 0xAA 0x55
    ↓ 找到
检查剩余长度是否够 6 字节头 → 不够则等下一包
    ↓ 够
读 LEN → 检查是否够 LEN+CRC → 不够则等下一包
    ↓ 够
取 CRC → 与本地计算的 CRC16 比较
    ├─ 一致 → 产出 Frame，buf.removePrefix(整帧长度)
    └─ 不一致 → crcErrorCount++，buf.removePrefix(1)   ← 关键
```

**出错只丢 1 字节**，而不是清空整个缓冲区。这样即使帧头被噪声污染，后面已经收到的好数据仍然能被救回来。这是本解析器最重要的一个设计点。

### 3.3.4 `ReconnectPolicy` —— 重连策略

```kotlin
object ReconnectPolicy {
    const val BASE_DELAY_MS = 1_000L
    const val MAX_DELAY_MS = 30_000L
    const val MAX_RETRY = 8

    fun delayFor(attempt: Int): Long {
        val raw = min(MAX_DELAY_MS, BASE_DELAY_MS shl attempt)   // 1s→2s→4s→…→30s
        val jitter = (raw * 0.3 * Random.nextDouble()).toLong()  // 0~30% 抖动
        return raw + jitter
    }
}
```

**为什么加随机抖动**：若所有设备在同一时刻断线（例如路由器重启、用户走出房间），固定延迟会让它们在完全相同的时刻一齐重连，造成"惊群"，反而把信道打满导致全部失败。加抖动把重试时刻打散。

### 3.3.5 `RuleEngine` —— 自动化规则引擎

```kotlin
class RuleEngine {
    private val hitCounters = mutableMapOf<Long, Int>()     // 规则 ID → 连续命中次数
    private val lastTriggerTime = mutableMapOf<Long, Long>() // 规则 ID → 上次触发时刻

    fun evaluate(rules: List<AutomationRule>, data: SensorData): List<AutomationRule>
}
```

判定逻辑三条：
1. 数值比较满足阈值 → `hit++`；不满足 → `hit = 0`（重置）
2. `hit >= rule.consecutiveHits` 才算达标（**防抖**：避免一次噪声就触发）
3. 距离上次触发 > 5 秒才允许再触发（**冷却**：避免疯狂刷通知）

另外提供 `HysteresisComparator`（滞回比较器）：温度 > 30 触发后，必须降到 < 28.5 才解除，避免在阈值附近反复横跳。

## 3.4 状态机设计

### 3.4.1 UI 状态

```kotlin
sealed interface UiState<out T> {
    object Idle : UiState<Nothing>
    object Loading : UiState<Nothing>
    object Empty : UiState<Nothing>
    data class Error(val message: String, val retry: (() -> Unit)? = null) : UiState<Nothing>
    data class Success<T>(val data: T) : UiState<T>
}
```

Fragment 中统一收集：

```kotlin
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.state.collect { render(it) }
    }
}
```

用 `repeatOnLifecycle(STARTED)` 而非 `launchWhenStarted`：后者在页面切后台时**只是暂停收集，Flow 上游仍在跑**，白白消耗资源；前者会真正取消上游。

### 3.4.2 连接状态

```kotlin
sealed interface ConnectionState {
    object Idle : ConnectionState
    object Scanning : ConnectionState
    object Connecting : ConnectionState
    data class Connected(val device: BleDevice) : ConnectionState
    data class Reconnecting(val attempt: Int, val nextDelayMs: Long) : ConnectionState
    data class Failed(val reason: String, val code: Int) : ConnectionState
    object Disconnected : ConnectionState
}
```

用密封接口而非枚举：需要携带数据（重试次数、错误码），枚举做不到。

## 3.5 线程模型

| 场景 | 线程 | 做法 |
|------|------|------|
| BLE 回调 | Binder 线程 | 立即 `trySend` 到 Channel，不阻塞 |
| 帧解析 | `Dispatchers.Default` | CPU 密集，走默认线程池 |
| 数据库读写 | `Dispatchers.IO` | Room 自带 IO 调度，DAO 挂起函数自动切 |
| UI 更新 | 主线程 | `StateFlow.collect` 在主线程 |
| 曲线绘制 | 主线程 `invalidate()` | 环形缓冲只读，绘制开销 O(点数) |

**原则**：全项目无 `Thread { }`、无 `Handler.postDelayed` 循环，一律协程。

## 3.6 三级降级设计

这是本项目应对"外部条件不满足"的核心策略。

| 级别 | 触发条件 | 降级方案 | 用户仍可使用的功能 |
|------|---------|---------|-------------------|
| L1 蓝牙权限被拒 | 用户拒绝 `BLUETOOTH_SCAN` | 设置页开放"手动 MAC 直连"输入框 | 全部功能（只要有 MAC） |
| L2 通知权限被拒 | 用户拒绝 `POST_NOTIFICATIONS` | 告警降级为 App 内 Snackbar 横幅 | 除系统通知外全部 |
| L3 无硬件 | 手头没有 ESP32 | 设置页开启"模拟数据源"，生成真实二进制帧走同一解析器 | 协议层、UI、规则、存储全部 |

**L3 的设计要点**：模拟数据源**不是直接伪造 `SensorData` 对象**，而是**生成真实的字节数组**再喂给 `FrameParser`。这样测的是完整链路——如果解析器有 bug，模拟模式同样会暴露。这是"降级但不降验证强度"的关键。
