## 5.1 自定义二进制协议帧

### 5.1.1 帧格式

```
┌──────┬──────┬──────┬──────┬──────┬─────────┬───────┐
│ SOF  │ VER  │ TYPE │ SEQ  │ LEN  │ PAYLOAD │ CRC16 │
│ 2B   │ 1B   │ 1B   │ 1B   │ 1B   │ NB      │ 2B    │
└──────┴──────┴──────┴──────┴──────┴─────────┴───────┘
 0xAA55  0x01                         大端
```

| 字段 | 作用 |
|------|------|
| SOF | 帧头 `0xAA 0x55`，两字节降低误判概率 |
| VER | 协议版本，便于将来升级兼容 |
| TYPE | 帧类型（数据 / 心跳 / 告警 / ACK / 命令） |
| SEQ | 循环序号 0-255，**用于检测丢包** |
| LEN | 载荷长度，使解析器能知道一帧有多长 |
| PAYLOAD | 实际数据，传感器帧固定 12 字节 |
| CRC16 | 校验，范围 = VER..PAYLOAD（不含 SOF 与 CRC 自身） |

### 5.1.2 为什么不用 JSON

| 维度 | JSON | 二进制帧 |
|------|------|---------|
| 一帧体积 | `{"t":26.5,"h":58.2,"p":1013.2,"l":320}` ≈ 45 B | 20 B |
| 解析开销 | 需要词法分析、字符串转浮点 | 位运算取整数再 ÷10 |
| MTU 分包 | 45 B 至少 3 包 | 20 B 刚好 1 包 |
| ESP32 内存 | 需要 JSON 库，堆占用大 | 无依赖，栈上组帧 |
| 校验 | 需额外加 | 天然带 CRC |

ESP32 只有 520 KB SRAM，且 BLE 单包默认仅 20 字节有效载荷。JSON 会让一次采样拆成 3 个包，分包重组逻辑更复杂、丢包概率更高。**在资源受限的嵌入式场景，二进制协议是正确选择。**

### 5.1.3 浮点数如何用整数传输

传感器读数如 `26.5℃` 若直接传 float（4 字节），还要处理字节序与 NaN。本项目**统一放大 10 倍转整数**：

```kotlin
// ESP32 端：26.5℃ → 265
uint16_t t = (uint16_t)(temp * 10);
// Android 端：265 → 26.5f
tempAht = u16(0) / 10f
```

优点：
- 温度精度 0.1℃ 足够（AHT20 本身只有 ±0.3℃）
- `uint16` 最大 65535，÷10 后 6553.5，远超量程
- 整数没有精度丢失与字节序歧义
- 12 字节载荷塞下 5 个量

### 5.1.4 载荷布局（12 字节）

| 偏移 | 长度 | 内容 | 缩放 |
|------|------|------|------|
| 0-1 | 2 | AHT20 温度 | ÷10 |
| 2-3 | 2 | 湿度 | ÷10 |
| 4-5 | 2 | 气压 | ÷10 |
| 6-7 | 2 | 光照 | ×1 |
| 8-9 | 2 | BMP280 温度 | ÷10 |
| 10 | 1 | 健康位 flags | — |
| 11 | 1 | 保留 | — |

## 5.2 CRC16 校验

### 5.2.1 实现

```kotlin
object Crc16 {
    private const val POLY = 0x1021
    private const val INIT = 0xFFFF

    fun ccittFalse(data: ByteArray, offset: Int = 0, length: Int = data.size): Int {
        var crc = INIT
        for (i in offset until (offset + length)) {
            crc = crc xor ((data[i].toInt() and 0xFF) shl 8)
            crc = crc and 0xFFFF
            repeat(8) {
                crc = if ((crc and 0x8000) != 0) {
                    ((crc shl 1) xor POLY) and 0xFFFF
                } else {
                    (crc shl 1) and 0xFFFF
                }
            }
        }
        return crc and 0xFFFF
    }
}
```

### 5.2.2 三个必须回答的问题

**Q：为什么 `data[i].toInt() and 0xFF`？**
Kotlin 的 `Byte` 是**有符号**的，范围 −128~127。`0xAA` 作为 Byte 是 `-86`，直接 `shl 8` 会得到 `-22016`，符号位污染整个计算。必须 `and 0xFF` 转成无符号的 `170`。这是 Kotlin/Java 位运算最常见的坑。

**Q：为什么 CRC 放最后而不是最前？**
CRC 是**余数**，除法必须从高位开始逐位推进，算完才知道余数是多少。放前面就必须先遍历一遍算出值再回填，或者把帧倒过来算——都不自然。放最后可以边组帧边算，一遍搞定。

**Q：CRC 能纠错吗？**
**不能**。CRC 只检错不纠错。本项目的策略是：检出错误 → 丢弃该帧 → 丢包计数 +1 → UI 显示 CRC 错误率。这比"把一个错的值显示给用户"要好得多。

### 5.2.3 检测能力

| 错误类型 | 能否检出 |
|---------|---------|
| 单比特错误 | 100% |
| 双比特错误（≤16 位间隔） | 100% |
| 奇数个比特错误 | 100% |
| 突发错误 ≤16 位 | 99.998% |
| 突发错误 = 17 位 | 99.997% |

## 5.3 流式帧解析（滑动窗口）

### 5.3.1 问题

BLE Notify 的分包边界与协议帧边界**毫无关系**：
- 一次回调可能只有半帧（20 字节 MTU，一帧 20 字节但由于时序可能被拆）
- 也可能一次回调带来两帧半

直接"收到一包就当一帧解析"必然丢数据。

### 5.3.2 解法

维护累积缓冲区，按状态机逐字节推进：

```
WAIT_SOF0 → WAIT_SOF1 → 收 VER/TYPE/SEQ/LEN → 收 PAYLOAD → 收 CRC → 校验
```

核心代码：

```kotlin
fun feed(data: ByteArray, length: Int = data.size): List<Frame> {
    val out = ArrayList<Frame>(2)
    for (i in 0 until length) {
        val b = data[i]
        when (size) {
            0 -> if (b == FrameSpec.SOF_0) buffer[size++] = b
            1 -> when {
                b == FrameSpec.SOF_1 -> buffer[size++] = b
                b == FrameSpec.SOF_0 -> buffer[0] = b    // AA AA：后一个 AA 可能是真帧头
                else -> size = 0
            }
            else -> {
                if (size >= capacity) { reset(); framesDropped++; continue }
                buffer[size++] = b
                if (size < HEADER_SIZE) continue
                val payloadLen = buffer[5].toInt() and 0xFF
                if (payloadLen > MAX_PAYLOAD) { dropOne(); framesDropped++; continue }
                val need = HEADER_SIZE + payloadLen + CRC_SIZE
                if (size < need) continue               // 还没收满，继续攒
                if (Crc16.verifyFrame(buffer.copyOfRange(0, need))) {
                    out.add(...); framesOk++; size = 0
                } else {
                    dropOne(); framesBadCrc++            // ★ 只丢 1 字节
                }
            }
        }
    }
    return out
}
```

### 5.3.3 为什么出错只丢 1 字节

若 CRC 校验失败就 `reset()` 清空缓冲区，会连带丢掉**后面已经收到的好数据**。只丢最老的 1 字节（`dropOne()` 做 `arraycopy` 前移），能保证不漏掉任何潜在的帧头位置。这就是**滑动窗口**思想，代价只是多循环几次。

这是本解析器最重要的设计点，也是与"教科书式简单解析"的分水岭。

### 5.3.4 丢包检测

```kotlin
val delta = (seq - prev + 256) % 256   // mod 256 处理 255→0 回绕
if (delta > 1) totalLost += (delta - 1)
```

SEQ 是 0-255 循环。用 mod 256 差值判断中间跳过了几个号。`+256` 是为了在 Kotlin 中避免负数取模。

## 5.4 指数退避重连

```kotlin
object ReconnectPolicy {
    const val BASE_DELAY_MS = 1_000L
    const val MAX_DELAY_MS = 30_000L
    const val MAX_RETRY = 8

    fun delayFor(attempt: Int): Long {
        val raw = min(MAX_DELAY_MS, BASE_DELAY_MS shl attempt)  // 1→2→4→8→…→30s
        val jitter = (raw * 0.3 * Random.nextDouble()).toLong() // 0~30% 抖动
        return raw + jitter
    }
}
```

| 尝试 | 基础延迟 | 加抖动后范围 |
|------|---------|-------------|
| 1 | 1s | 1.0 ~ 1.3s |
| 2 | 2s | 2.0 ~ 2.6s |
| 3 | 4s | 4.0 ~ 5.2s |
| 4 | 8s | 8.0 ~ 10.4s |
| 5 | 16s | 16.0 ~ 20.8s |
| 6+ | 30s（封顶） | 30.0 ~ 39.0s |

**为什么指数而不是固定间隔**：设备刚断线时（走出房间、临时遮挡）很可能马上能连上，快速重试能快速恢复；若长时间连不上，说明是真的离开了，继续每秒重试只是白耗电。指数退避在"快速恢复"与"省电"之间取得平衡。

**为什么加随机抖动**：若多台设备在同一时刻断线（走出房间），固定延迟会让它们在**完全相同的时刻**一齐重连，造成"惊群效应"，反而把信道打满导致全部失败。加 0~30% 抖动把重试时刻打散。

**常见 BLE 错误码**（UI 上会显示中文释义）：

| 码 | 含义 | 处理 |
|----|------|------|
| 133 | `GATT_ERROR`，协议栈层通用失败 | 退避重试 |
| 8 | `GATT_CONN_TIMEOUT`，连接超时 | 退避重试 |
| 22 | `GATT_CONN_TERMINATE_PEER_USER`，对端主动断开 | 立即重试一次 |
| 257 | `GATT_AUTH_FAIL`，配对失败 | 提示用户重新配对 |

## 5.5 卡尔曼滤波

### 5.5.1 五公式（标量版）

```
① 预测状态：   x̂⁻ = x̂              （温度不会突变，预测 = 上一刻最优值）
② 预测协方差： P⁻ = P + Q
③ 卡尔曼增益： K  = P⁻ / (P⁻ + R)
④ 更新状态：   x̂  = x̂⁻ + K(z − x̂⁻)   ← 实际输出
⑤ 更新协方差： P  = (1 − K) · P⁻
```

```kotlin
override fun filter(value: Float): Float {
    if (!initialized) { estimate = value; initialized = true; return estimate }
    errorCov += processNoise                       // ② P⁻ = P + Q
    val gain = errorCov / (errorCov + measureNoise) // ③ K = P⁻/(P⁻+R)
    _lastGain = gain
    estimate += gain * (value - estimate)           // ④ x̂ = x̂⁻ + K(z−x̂⁻)
    errorCov *= (1 - gain)                          // ⑤ P = (1−K)P⁻
    return estimate
}
```

### 5.5.2 参数 Q / R 怎么调

| 参数 | 含义 | 调大的效果 | 本项目取值 |
|------|------|-----------|-----------|
| Q（过程噪声） | 认为真实值变化多快 | 更信测量 → 响应快但抖 | **0.01**（室内温度每秒变化远小于 0.01℃） |
| R（测量噪声） | 传感器自身噪声 | 更信预测 → 平滑但迟钝 | **0.1**（AHT20 标称 ±0.3℃，方差 ≈ 0.09） |

**K 会自动收敛**：刚开始 P 大 → K≈1 → 几乎全信测量（快速跟上真值）；随着 P 逐渐减小 → K 变小 → 越来越信预测（输出越来越平滑）。这个收敛过程是卡尔曼滤波优于固定窗口平均的本质原因。

### 5.5.3 与滑动平均对比

| 维度 | 滑动平均(N=5) | 卡尔曼 |
|------|--------------|--------|
| 阶跃响应 | 约 5 个周期 | 约 3 个周期 |
| 稳态抖动 | 基准 | 约为一半 |
| 历史权重 | 全部相同 | 指数衰减，近的权重大 |
| 参数 | 窗口大小 | Q / R，有物理含义 |

UI 上可实时切换三种模式（原始 / 滑动平均 / 卡尔曼），这是演示亮点。

## 5.6 规则引擎防抖

### 5.6.1 三重防线

```kotlin
fun evaluate(rules: List<AutomationRule>, data: SensorData): List<AutomationRule> {
    val triggered = mutableListOf<AutomationRule>()
    for (rule in rules) {
        if (!rule.enabled) continue
        val value = data.valueOf(rule.channel)
        if (rule.operator.matches(value, rule.threshold)) {
            hitCounters[rule.id] = (hitCounters[rule.id] ?: 0) + 1
        } else {
            hitCounters[rule.id] = 0          // ① 不满足立刻清零
            continue
        }
        if (hitCounters[rule.id]!! < rule.consecutiveHits) continue  // ② 防抖
        val now = System.currentTimeMillis()
        if (now - (lastTriggerTime[rule.id] ?: 0) < COOLDOWN_MS) continue  // ③ 冷却
        lastTriggerTime[rule.id] = now
        triggered.add(rule)
    }
    return triggered
}
```

| 防线 | 作用 | 不做的后果 |
|------|------|-----------|
| 连续命中 N 次 | 防噪声误报 | 一次尖峰就触发，误报频繁 |
| 5 秒冷却 | 防刷屏 | 达标期间每帧触发一次，通知栏爆炸 |
| 滞回比较 | 防阈值抖动 | 温度在 30.0 上下跳 → 反复触发/解除 |

### 5.6.2 滞回比较器

温度 > 30.0 触发报警后，必须降到 < 28.5 才解除。中间 1.5℃ 的"死区"避免了在阈值临界点反复横跳。这是温控器、比较器电路（施密特触发器）的标准做法。

class DatabaseCleanupWorker(ctx: Context, params: WorkerParameters) : CoroutineWorker(ctx, params) {

## 5.9 实时曲线自绘

`RealtimeChartView` 用 Canvas 绘制，核心是**环形缓冲**：

```kotlin
private val buffer = FloatArray(CAPACITY)   // 固定 300 点
private var head = 0                        // 写入位置

fun push(v: Float) {
    buffer[head] = v
    head = (head + 1) % CAPACITY            // 满了自动覆盖最老的
    invalidate()
}
```

**为什么用环形缓冲而不是 ArrayList**：
- 固定容量，永不 GC 压力（每秒 1 次 × 300 点，ArrayList 会反复扩容/搬家）
- 覆盖写入，天然实现"滚动窗口"效果
- 绘制时按 `(head + i) % CAPACITY` 顺序读，保证从左到右是时间正序

未使用任何图表库（MPAndroidChart 等），纯自绘，减少依赖也体现基本功。
