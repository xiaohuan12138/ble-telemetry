# 答辩问答预测题与标准答案

> 分五类：BLE 基础 / 协议与校验 / 架构与 Android / 算法 / 工程与诚实性问题。
> 每题给出「一句话答案」+「展开回答」。**先答一句话，再展开**——老师时间有限。

---

## A 类：BLE 基础（必问）

### A1. BLE 和普通蓝牙（耳机那个）是一回事吗？

**一句话**：不是。它们是两套独立的协议栈，互相不兼容。

**展开**：
- **经典蓝牙（BR/EDR）**：为持续音频流设计，带宽约 2-3 Mbps，功耗高，用于耳机、音箱、车载。
- **BLE（Bluetooth Low Energy）**：4.0 引入，为间歇性小数据设计，1 Mbps 物理速率、实际吞吐只有 5-30 KB/s，但待机电流可低至微安级，一颗纽扣电池能跑一两年。
- 手机芯片通常是**双模**的，所以你感觉不到区别；但 ESP32-WROOM-32 也是双模，本项目只用 BLE 那部分。
- 我们的数据量是每秒几十字节，BLE 绰绰有余，而且要长时间工作，所以选 BLE。

---

### A2. 什么是 GATT？Service / Characteristic / Descriptor 是什么关系？

**一句话**：GATT 是 BLE 里组织数据的层级结构，像文件系统：Service 是文件夹，Characteristic 是文件，Descriptor 是文件的属性。

**展开**：
- **Service**：一组相关功能的集合。我用两个自定义 Service——`FF10` 传感器服务、`FF20` 控制服务；另外还挂了标准的设备信息服务 `180A` 和电量服务 `180F`。
- **Characteristic**：真正读写数据的端点，带属性（Read / Write / Notify / Indicate）。数据特征 `FF11` 是 Notify（设备主动推），控制特征 `FF21` 是 Write（手机下发）。
- **Descriptor**：描述特征的元数据。最关键的是 **CCCD（0x2902）**，它是 Notify 的开关。
- 手机是 **GATT Client**，ESP32 是 **GATT Server**——注意这和"谁发起连接"无关，只表示谁提供服务。

---

### A3. 为什么测温度、湿度、气压、光照？这些和"蓝牙设备控制"有什么关系？

**一句话**：因为"控制"必须有依据——没有传感器反馈的控制叫盲控，那是开关，不是系统。

**展开**：
这四个量构成一个完整的环境感知闭环：
- **温度**：最通用的控制触发源（过热告警、恒温控制）
- **湿度**：与温度耦合（体感、结露判断）
- **气压**：可换算海拔，也能反映天气趋势
- **光照**：昼夜判断（自动开灯）

**关系是这样的**：传感器产生数据 → 数据通过 BLE 传到手机 → 手机按规则判断 → 判断结果触发控制动作（LED / 蜂鸣器）→ 动作改变了物理环境 → 又被传感器测到。

**这是个闭环**。如果只是"手机发个指令让灯亮"，那用个红外遥控器也行，根本不需要蓝牙双向通信。正因为要**双向**——上行传数据、下行发指令——才需要 BLE 这种双向链路。传感器是这个闭环的输入端，没有它们，控制就失去了意义。

---

### A4. 为什么连上了却收不到数据？

**一句话**：漏了 CCCD 那一步。

**展开**：订阅 Notify 必须做**两件事**：

```kotlin
// ① 告诉手机本地协议栈：我要收这个特征的通知
bluetoothGatt.setCharacteristicNotification(char, true)
// ② 告诉对端设备：请开始推送
desc.value = BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE
bluetoothGatt.writeDescriptor(desc)
```

只做 ① 的话，手机这边准备好了，但 ESP32 根本不知道有人在听，自然不会推。表现就是：连接成功、服务发现成功、`onConnectionStateChange` 收到 `STATE_CONNECTED`，但 `onCharacteristicChanged` 永远不回调。

这是 BLE 开发最常见的坑，我在文档里专门标注了。

---

### A5. Notify 和 Indicate 有什么区别？为什么选 Notify？

| | Notify | Indicate |
|---|--------|----------|
| 确认机制 | 无，发完就不管 | 需要对端回确认 |
| 速度 | 快 | 慢（要等 ACK） |
| 可靠性 | 可能丢 | 不丢 |

**为什么选 Notify**：传感器数据是**连续采样**，丢一帧下一帧马上补上，无所谓；但如果用 Indicate，每帧都要等确认，吞吐直接减半，对 1Hz 以上的采样很不利。真正需要保证送达的是**命令**，我对命令做了 **ACK 帧**机制——ESP32 执行完回一个 `0x41` 状态码帧，这是应用层确认，比链路层 Indicate 更灵活（能带上"参数错误"这种语义）。

## B 类：协议与校验

### B1. 为什么不用 JSON？

**一句话**：太大、太慢、还得拆包。

**展开**：

| 维度 | JSON | 二进制帧 |
|------|------|---------|
| 一帧体积 | `{"t":26.5,"h":58.2,"p":1013.2,"l":320}` ≈ 45 B | 20 B |
| MTU 分包 | 45 B 至少 3 包 | 20 B 刚好 1 包 |
| 解析开销 | 词法分析 + 字符串转浮点 | 位运算取整数 ÷10 |
| ESP32 内存 | 需 JSON 库，堆占用大 | 无依赖，栈上组帧 |
| 校验 | 要额外加 | 天然自带 |

ESP32 只有 520 KB SRAM，BLE 单包默认仅 20 字节有效载荷。JSON 一次采样拆 3 包，分包重组逻辑更复杂、丢包概率更高。**资源受限的嵌入式场景，二进制协议是正确选择。**

---

### B2. CRC 的三个参数是什么？为什么是这些值？

**一句话**：CRC-16/CCITT-FALSE，多项式 0x1021，初值 0xFFFF，输入输出不反射、输出不异或。

**展开**：
这三个参数**唯一确定一个 CRC 变体**。常见变体还有 CRC-16/MODBUS（初值 0xFFFF 但输入反射）、CRC-16/IBM（初值 0x0000）。参数不一致，算出来的值完全不同，两端必须统一。

我选 CCITT-FALSE 是因为它是嵌入式领域最通用的一个，ESP32 端实现简单，且检错能力足够：单比特 100%、双比特 100%、奇数个比特 100%、16 位以内突发错误 99.998%。

---

### B3. CRC 能纠错吗？

**一句话**：不能。CRC 只检错，不纠错。

**展开**：
检错是"发现数据坏了"，纠错是"把坏的数据修好"。纠错需要冗余度更高的编码，比如海明码（能纠 1 位）、里德-所罗门码（CD、二维码用）。

我的策略是：**检出错误 → 丢弃该帧 → 丢包计数 +1 → UI 显示 CRC 错误率**。

为什么不纠错？因为传感器数据是连续采样的，**丢一帧的成本是零**（下一帧马上来），而纠错的代价是要多传冗余字节、MCU 上多算一遍——不划算。宁可丢，不可错：显示一个错误的 154.1℃ 比不显示要糟糕得多。

---

### B4. 为什么 CRC 放在帧尾而不是帧头？

**一句话**：CRC 是余数，除法必须从高位逐位推进，算完才知道余数是多少。

**展开**：
CRC 本质是多项式除法取余。除法的顺序决定了：必须先把所有数据位喂进去，才能得到余数。放帧头的话，就要么先遍历一遍算出值再回填（两遍），要么把帧倒过来算（不自然）。放帧尾可以**边组帧边算，一遍搞定**，CRC 算完直接追加在后面。

顺带：接收端校验时，把帧尾 2 字节取出来，与前面临时算的余数比对即可。

---

### B5. 校验范围为什么不包括 SOF？

**一句话**：SOF 的作用就是"被识别"，它出错不会被当成数据，而是直接被解析器跳过。

**展开**：
- SOF 是帧同步标志，解析器靠 `0xAA 0x55` 对齐帧边界。如果 SOF 本身被干扰了，解析器只会**找不到这个帧头**，继续往下找——不会解析出错误数据。
- 把 SOF 纳入校验没有收益，反而让校验逻辑变复杂（要先跳过 2 字节）。
- 同理，校验范围也不包括 CRC 自身那 2 字节——自己校验自己没有意义。
- 所以范围是 **VER..PAYLOAD**，即 `offset=2, length=4+payloadLen`。

---

### B6. 浮点数怎么用整数传？

**一句话**：放大 10 倍转 uint16，接收端 ÷10 还原。

**展开**：
- 26.5℃ → 265（uint16）→ 接收端 265 / 10f = 26.5f
- **精度够**：AHT20 标称 ±0.3℃，0.1℃ 分辨率绰绰有余
- **量程够**：uint16 最大 65535，÷10 后 6553.5，远超所有传感器量程
- **无歧义**：整数没有 IEEE754 的 NaN / 无穷 / 次正规数，也没有字节序歧义（我用大端，两端统一）
- **省空间**：12 字节塞下 5 个物理量 + 健康位 + 保留位

---

### B7. SEQ 字段有什么用？怎么判断丢包？

**一句话**：SEQ 是 0-255 的循环序号，固件每发一帧 +1；接收端用 mod 256 差值判断中间跳过了几个号。

**展开**：
```kotlin
val delta = (seq - prev + 256) % 256   // +256 避免 Kotlin 负数取模
if (delta > 1) totalLost += (delta - 1)
```
- `delta == 1`：正常
- `delta == 2`：中间丢了 1 帧
- `delta <= 0`：回绕了（255 → 0），mod 修正后是 1，正确

这个设计让我能在 UI 上显示"丢包率"，这是**可靠性可观测**——不是"我觉得它应该没问题"，而是"我测量了它确实没问题"。

## C 类：架构与 Android

### C1. 为什么用 MVVM？

**一句话**：为了让 Activity/Fragment 只管画界面，业务逻辑能独立于 Android 生命周期被测试和复用。

**展开**：
- **传统做法的问题**：把网络请求、数据库操作写在 Activity 里 → 屏幕旋转 Activity 重建 → 数据丢失；而且 Activity 越来越臃肿，无法测试。
- **MVVM 的解法**：ViewModel 的生命周期比 Activity 长，屏幕旋转时 ViewModel 不重建，数据保住了。
- 我的 ViewModel 暴露 `StateFlow<UiState>`，Fragment 只做一件事：`collect` 然后 `render`。
- **收益**：`protocol/` 和 `domain/` 两层完全不依赖 Android，纯 Kotlin，5 个测试类就能覆盖核心算法。这是分层带来的直接好处。

---

### C2. 为什么用 `repeatOnLifecycle(STARTED)` 而不是 `launchWhenStarted`？

**一句话**：`launchWhenStarted` 只是暂停收集，上游 Flow 还在跑；`repeatOnLifecycle` 会真正取消上游。

**展开**：
```kotlin
// ❌ 不好：页面切后台时上游仍在发射，白白消耗资源
viewLifecycleOwner.lifecycleScope.launchWhenStarted {
    viewModel.data.collect { ... }
}

// ✅ 正确：切后台时取消上游，回前台重新启动
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.data.collect { ... }
    }
}
```
对我们的场景尤其重要：BLE 数据每秒来一帧，如果页面在后台还继续收集并写数据库，就是在白耗电。`repeatOnLifecycle` 是 Google 官方推荐写法。

---

### C3. `callbackFlow` 用在哪？为什么需要它？

**一句话**：把 BLE 的 Java 回调接口包装成 Kotlin 协程的 Flow，让异步回调能用在挂起函数里。

**展开**：
Android 的 `BluetoothGattCallback` 是回调式的，而且有个硬约束：**同一时刻只能有一个 GATT 操作在飞**，必须排队。手写回调会陷入"回调地狱"。

我用 `callbackFlow` + `Channel` 把它转成挂起函数，调用方写起来是同步顺序的：
```kotlin
suspend fun enableNotification(uuid: UUID): Boolean {
    gatt.setCharacteristicNotification(char, true)
    return writeDescriptor(desc)   // 挂起等待 onDescriptorWrite 回调
}
```
读起来像同步代码，实际不阻塞线程。这是协程在 Android 上最典型的价值。

---

### C4. Room 三张表为什么这么设计？

**一句话**：`readings` 存历史、`rules` 存规则、`devices` 记住连过的板子；`readings` 与 `devices` 是一对多的逻辑关联。

**展开**：
- **`readings`**：支撑历史页和统计。建了 `deviceAddress` 和 `timestamp` 两个索引，分别加速"按设备筛选"和"按时间排序"。
- **`rules`**：规则必须持久化，否则重启 App 用户配的规则全没了。
- **`devices`**：记住上次连过的设备，下次打开直接显示，不用重新扫。

**为什么不用真正的外键约束**：如果加 `ForeignKey(onDelete = CASCADE)`，删掉一个设备会连带删掉它全部历史读数——这不是我要的。历史数据有价值，设备记录只是缓存。所以只做逻辑关联 + 索引。

---

### C5. 为什么 DAO 返回 Flow 而不是 List？

**一句话**：返回 Flow，数据库内容变化时会自动重新发射，UI 完全不用手动刷新。

**展开**：
底层是 SQLite 的 trigger + Room 的 `InvalidationTracker`：Room 会监听表的变更，一旦 INSERT/UPDATE/DELETE，就重新执行查询并发射新值。

这一条**直接消灭了"插入后忘了 notifyDataSetChanged"这类经典 bug**。历史页我插入一条新读数，列表自动就出来了，代码里没有任何刷新调用。

另外所有 DAO 方法标 `suspend`，Room 有严苛的线程检查——在主线程调用会直接崩，强制你放进协程，天然避免 ANR。

---

### C6. 为什么要做数据裁剪？

**一句话**：1Hz 采样跑一天就是 86400 条，不裁剪数据库会无限膨胀。

**展开**：
```sql
DELETE FROM readings WHERE id NOT IN (
    SELECT id FROM readings ORDER BY timestamp DESC LIMIT :keep)
```
用 `WorkManager` 的 `PeriodicWorkRequest` 每 12 小时跑一次，保留最近 10000 条。

**为什么用 WorkManager 而不是自己起定时器**：WorkManager 由系统统一调度，会遵守省电策略（Doze 模式）、进程被杀后能恢复、不用自己处理各种边界情况。自己写 `Handler.postDelayed` 循环，进程一死就没了。

---

### C7. 权限被拒了怎么办？

**一句话**：三级降级。

**展开**：
| 级别 | 触发 | 降级方案 | 剩余可用功能 |
|------|------|---------|-------------|
| L1 | 拒 `BLUETOOTH_SCAN` | 设置页开放手动输入 MAC 直连 | 全部（只要有 MAC） |
| L2 | 拒 `POST_NOTIFICATIONS` | 告警降级为 App 内 Snackbar | 除系统通知外全部 |
| L3 | 没有 ESP32 硬件 | 开启模拟数据源 | 协议、UI、规则、存储全部 |

**L3 的关键设计**：模拟数据源**不是直接伪造 `SensorData` 对象**，而是**生成真实的字节数组**再喂给同一个 `FrameParser`。这样测的是完整链路——如果解析器有 bug，模拟模式同样会暴露。这是"降级但不降验证强度"。

---

### C8. `UiState` 是什么？为什么要它？

**一句话**：密封接口统一描述加载、空、错误、成功四种状态，避免 UI 状态散落在各种布尔变量里。

**展开**：
```kotlin
sealed interface UiState<out T> {
    object Idle : UiState<Nothing>
    object Loading : UiState<Nothing>
    object Empty : UiState<Nothing>
    data class Error(val message: String, val retry: (() -> Unit)? = null) : UiState<Nothing>
    data class Success<T>(val data: T) : UiState<T>
}
```
**不用它的下场**：`isLoading`、`isEmpty`、`errorMsg`、`data` 四个变量各自为政，很容易出现 `isLoading=true` 且 `errorMsg!=null` 这种自相矛盾的状态，UI 就显示错乱。

用密封接口 + `when` 表达式，编译器强制你**穷举所有情况**，少处理一种就编译不过。这是 Kotlin 密封类型最实用的场景。

## D 类：算法

### D1. 卡尔曼滤波五个公式，你的 Q 和 R 为什么这么取？

**一句话**：Q=0.01 因为室内温度每秒变化远小于这个量级；R=0.1 因为 AHT20 标称精度 ±0.3℃，方差约 0.09。

**展开**：
五公式（标量版）：
```
① x̂⁻ = x̂              （温度不会突变，预测 = 上一刻最优值）
② P⁻ = P + Q
③ K  = P⁻ / (P⁻ + R)
④ x̂  = x̂⁻ + K(z − x̂⁻)   ← 实际输出
⑤ P  = (1 − K) · P⁻
```

**参数含义**：
- **Q（过程噪声）**：认为真实值变化多快。Q 大 → 更信测量 → 响应快但抖
- **R（测量噪声）**：传感器自身噪声。R 大 → 更信预测 → 平滑但迟钝

**K 会自动收敛**：刚开始 P 大 → K≈1 → 几乎全信测量（快速跟上真值）；随着 P 减小 → K 变小 → 越来越信预测（输出越来越平滑）。这个收敛过程是卡尔曼优于固定窗口平均的本质原因。

---

### D2. 卡尔曼和滑动平均比，好在哪？

| 维度 | 滑动平均(N=5) | 卡尔曼 |
|------|--------------|--------|
| 阶跃响应 | 约 5 个周期 | 约 3 个周期 |
| 稳态抖动 | 基准 | 约为一半 |
| 历史权重 | 全部相同 | 指数衰减，近的权重大 |
| 参数含义 | 窗口大小（纯经验） | Q / R（有物理意义） |

**最本质的区别**：滑动平均的固定窗口是"拍脑袋"定的，卡尔曼的增益是**根据不确定性自动算出来的**，会自适应。而且卡尔曼是递推的，不需要保存历史样本——滑动平均要存 N 个，卡尔曼只存 2 个标量（估计值和协方差）。MCU 上这点尤其重要。

---

### D3. 重连为什么用指数退避？为什么加随机抖动？

**一句话**：指数是为了平衡"快速恢复"与"省电"；抖动是为了避免多台设备同时重连的惊群效应。

**展开**：
- **指数**：刚断线（走出房间、临时遮挡）很可能马上能连上，快速重试快速恢复；长时间连不上说明真离开了，继续每秒重试只是白耗电。所以 1s → 2s → 4s → … → 30s 封顶。
- **抖动**：若所有设备在同一时刻断线，固定延迟会让它们在**完全相同的时刻**一齐重连，瞬间把信道打满，反而全部失败。加 0~30% 抖动把重试时刻打散。

这不是我发明的，是 TCP 拥塞控制、以太网 CSMA/CD 的标准做法。

---

### D4. 规则引擎为什么需要三重防抖？

| 防线 | 作用 | 不做的后果 |
|------|------|-----------|
| 连续命中 N 次 | 防噪声误报 | 一次尖峰就触发 |
| 5 秒冷却 | 防刷屏 | 达标期间每帧触发，通知栏爆炸 |
| 滞回比较 | 防阈值抖动 | 温度在 30.0 上下跳 → 反复触发/解除 |

**展开**：
- **连续命中**：廉价 MEMS 传感器有随机噪声，静止时温度可能在 30.1 / 29.8 / 30.2 之间跳。只判一次就会误报。连续 N 次（默认 3）说明是真超标，不是噪声。
- **冷却**：温度一旦超标，会持续超标。没有冷却的话每秒触发一次通知，用户会直接关掉通知权限。
- **滞回**：温度在阈值临界点抖动时，会反复触发-解除-触发。加 1.5℃ 死区（>30.0 触发，<28.5 才解除）彻底解决。这是施密特触发器的思路，温控器都这么做。

---

### D5. 为什么两个传感器都能测温（AHT20 和 BMP280）？不是浪费吗？

**一句话**：这是冗余设计——两颗芯片互相当对方的校验，任一漂移都能立刻发现。

**展开**：
BMP280 本来就是为测气压买的，它顺带能测温是"白送的"。我把它用起来做交叉校验：
```kotlin
val tempConsistent: Boolean
    get() = kotlin.math.abs(tempAht - tempBmp) <= 2.0f
```
- 两颗芯片差值 ≤ 2℃ 认为正常
- 超过就说明**至少有一颗出问题了**（虚焊、进水、老化漂移）
- 主温度显示优先用 AHT20（精度 ±0.3℃ vs BMP280 的 ±1℃），AHT20 失效时自动回退到 BMP280

**成本**：零（BMP280 本来就要买）。**收益**：有了故障自诊断能力。这在工业上叫"冗余表决"，是最基础的可靠性手段。
